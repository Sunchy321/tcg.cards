## 实施原则

以 `MERGE_HEAD` 对应的 `upstream/dev` 为功能基线，以 `ORIG_HEAD` 对应的 `sub` 为视觉参考。页面修改采用小步移植，不用任一旧文件整体替换 `dev` 文件。

## 第一阶段：范围清理

1. 恢复炉石服务端、部署配置、临时脚本和数据库连接文件为 `dev` 版本。
2. 确认炉石 schema、迁移、导入与发布目录相对 `dev` 没有差异。
3. 建立允许保留的 UI 文件与资源清单。

## 第二阶段：视觉基础

1. 对照两侧的 `app.config.ts` 与全局 CSS，合并炉石主题变量。
2. 保留实际会被页面引用的职业、系列和数值图标，清除重复或无引用资源。
3. 保持 `dev` 新组件 API，不恢复旧 CardImage 实现。

## 第三阶段：页面移植

1. 首页：保留设置、公告、随机卡牌、卡包与高级搜索行为，移植 `sub` 的入口卡片层级与背景风格。
2. 搜索：保留查询 DSL、排序、布局切换和用户配置同步，移植结果卡片和筛选反馈样式。
3. 高级搜索：在现有 Slideover 内应用炉石专属筛选层级、图标和交互反馈。
4. 卡牌详情：保留共享卡图、公告、版本和英雄技能信息，移植属性区、赛制与响应式排版。
5. 卡包列表：保留当前数据源，移植系列图标、分组与列表视觉。

## 第四阶段：验证

1. 分别检查浅色和深色主题以及桌面、窄屏布局。
2. 验证账户设置、公告、时间线、语言切换、随机卡牌、高级搜索和搜索结果跳转。
3. 使用 Bun 1.3.10 执行冻结锁文件安装、炉石类型检查和构建。
4. 审查 `git diff --cached MERGE_HEAD`，确认只有获准范围，且不存在炉石数据链路改动。

## 第五阶段：交付

1. 报告实现内容、验证结果和剩余风险。
2. 按炉石 UI、影之诗、游戏王三个主题准备独立 PR 边界。
3. 在用户确认提交信息前不创建提交。
