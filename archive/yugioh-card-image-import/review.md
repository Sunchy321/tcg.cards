# 游戏王第一版主卡图导入设计复核

## 结论

设计可以进入实施。用户已经确认 `ygopro` 来源，并同意先检查后复用现有 Hearthstone 卡图存储模式；现有仓库明确使用本地 R2-layout bucket 与 Cloudflare `R2_ASSET`，因此不引入新的对象存储供应商。

## 复核要点

- 实施期真实来源出现 `0.webp`，因此将其限定为可解析但不可映射的特殊来源记录；这避免来源格式变化导致整批不可用，同时不把零卡密恢复为领域标识。
- 下载 URL 保留 metadata 原始文件名，来源记录 ID 仅用于规范化映射与重复检测。

1. 领域模型保持第一版最小范围：一张卡只有一张主图，图片事实直接附着在 `yugioh.cards`，避免提前建立异画实体和第二套发布器。
2. 来源状态与批次留在 local `yugioh_data`，依赖方向为 `yugioh_data → yugioh`。
3. 关联只使用规范化八位卡密到 metadata 十进制文件名的确定转换，不使用卡名和 cid。
4. 本地文件采用内容寻址 key，来源变化不会覆盖旧缓存；领域软删除不触发对象物理删除。
5. 现有方案 A 卡牌发布器只需扩展字段覆盖，不改变卡牌 ID 策略或 remote 权威边界。
6. R2 同步维持现有独立执行方式；desktop 不保存 R2 access key，网站启动不上传或下载图片。
7. 完整来源约 1.90 GiB，实施验证应使用 fixture、真实 metadata 和单张真实图片，不自动触发完整下载。

## 已拒绝方案

- 直接热链百鸽 CDN：来源明确建议大流量项目自行缓存或镜像，且无法保证稳定性。
- 图片二进制写入 PostgreSQL：扩大数据库和发布负担，不符合现有 R2 模式。
- 复用 Hearthstone 渲染实现：游戏王来源已经提供 WebP，不需要 PNG 渲染、模板或 premium 变体。
- 第一版建立多图/异画实体：超出当前需求；待异画需求出现后单独迁移。
- desktop 直接持有 R2 access key：增加凭据面，并与现有“本地 bucket、独立同步”模式不一致。

## 实施提醒

- 所有新增函数和类型必须有简短英文用途注释。
- 先写 metadata、WebP、幂等决策和发布字段测试。
- Drizzle schema 先改定义，再生成 local/remote migration。
- 不运行 lint，不启动项目，不下载完整 1.90 GiB，不连接 production。

## 实施后复核

### Standards 轴

首次发现两项明确问题：测试注释使用了仓库禁止的元表述，设置页文案暴露了对象存储与同步实现细节。两项均已修复，复核未再发现函数/类型英文注释、前端文案、schema 依赖或 desktop 执行边界问题。

### Spec 轴

首次发现 metadata 内部空行与大小写校验不够严格、下载没有保留来源原始文件名、bucket/写入字节校验不完整，以及导入恢复缺少数据库集成测试。实现与 spec 已同步修正，并新增显式环境变量启用的隔离 PostgreSQL 集成测试，覆盖单图失败隔离、相同快照零下载、原图保留、缺文件恢复和来源消失软删除。复核未发现剩余高置信缺口或范围扩张。

### 验证结论

- runtime：63 项通过，1 项隔离数据库集成测试因未配置 `YUGIOH_IMAGE_TEST_DATABASE_URL` 正常跳过。
- 数据库：DB typecheck、local Drizzle check、remote Drizzle check 全部通过。
- desktop：Rust `cargo check --lib` 通过；Nuxt typecheck 被现有 npm 包解析错误阻断，未执行安装。
- 真实来源：严格解析 14,950 条记录，总大小 2,041,699,644 字节；青眼白龙 `89631139.webp` 下载、MD5/SHA-256、680×986 尺寸、本地内容寻址写入与回读校验通过。
- 未执行完整约 1.90 GiB 卡图导入、实际测试 remote 发布或 production 连接。
