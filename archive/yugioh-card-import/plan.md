## 实施原则

- desktop 是唯一导入与发布执行端；网站和普通前端部署不获得数据库写入能力。
- local PostgreSQL 是领域数据构建权威，remote 只接收 desktop 发布的受限副本。
- local → remote 显式保留 `yugioh.cards.id`，并在发布完成后校准 remote identity sequence。
- 所有领域删除均通过 `deleted_at` 表达，发布器不物理删除游戏王卡牌。
- 第一版只处理固定百鸽 JSON ZIP 来源和卡牌基础事实。
- 不读取或修改排除的应用，不顺手重构现有 Hearthstone 发布代码。
- 不连接 production，不把连接字符串、密码、`.env`、数据库文件或下载缓存写入仓库。
- 不运行 lint；验证仅使用相关测试、TypeScript typecheck、Drizzle 生成/检查和明确的测试数据源检查。

## 第一步：数据库 schema 与迁移

1. 在 shared 游戏王 schema 中定义 `yugioh.cards`，使用 `BIGINT GENERATED BY DEFAULT AS IDENTITY` 主键、可空唯一 cid、可空唯一八位卡密、来源事实字段、审计时间和 `deleted_at`。
2. 在 local 游戏王 schema 中定义来源映射、导入批次、失败、状态、发布批次、逐行计划和 baseline。
3. 在 remote 游戏王 schema 中复用 shared card 表并增加 publish ledger。
4. 更新 `@tcg-cards/db` 的 package exports、local/remote schema 入口和 Drizzle 配置。
5. 运行 `drizzle-kit generate` 分别生成 local 和 remote migration，不手工修改生成的 schema SQL 或 snapshot。
6. 检查 migration 包含两个 schema 轨道所需对象，且 `yugioh` 不引用 `yugioh_data`。

验证：运行 db package typecheck、Drizzle check，并检查生成 migration 的依赖方向和唯一约束。

## 第二步：数据源解析器

1. 先建立小型内存 fixture，覆盖正常记录、可选字段缺失、零卡密、七位卡密、负数值哨兵和 Unicode 正文。
2. 测试 ZIP 结构、JSON 根对象、根键/cid 一致性、重复 cid/卡密和未知字段摘要。
3. 使用受限 ZIP 中央目录解析器在内存中读取 ZIP；仅接受单卷、未加密的 stored/deflate `cards.json`，校验 CRC 和大小，并拒绝 HTML、损坏 ZIP、路径穿越和非预期文件结构。Bun 归档 API 当前没有该 ZIP 的读取接口。
4. 将来源记录规范化为固定字段对象并计算稳定 SHA-256。

验证：运行解析器单测，并对真实 `https://ygocdb.com/api/v0/cards.zip` 做一次下载与解析检查；临时数据只放系统临时目录或内存并在检查后清理。

## 第三步：本地幂等导入

1. 把身份决策提取为可纯测试的逻辑：来源映射优先，其次分别核对 cid 和卡密，禁止卡名匹配。
2. 实现导入批次状态、四项核心统计、失败明细和 import state。
3. 使用逐条 savepoint 隔离约束错误；结构性快照错误在领域写入前终止整批。
4. 通过 `(source, source_record_id)` 和 `source_hash` 保证重复导入跳过。
5. 完整快照结束后退休缺失来源映射，并只在没有 active 映射时设置卡牌 `deleted_at`；重新出现恢复原 ID。
6. 将崩溃遗留的 running 批次标记为 interrupted，让下一批依靠幂等映射续做。

验证：运行导入单元/集成测试，确认连续两次导入总数不增长、失败记录不误删已有卡牌、无卡密记录仍有内部 ID。

## 第四步：测试 remote 发布

1. 按现有 target ID、环境、实时数据库身份和指纹模式建立游戏王独立测试目标配置。
2. 发布前拒绝非 `test` 环境，并预检 remote 的 ID、cid、卡密是否与 local 漂移。
3. 对包含软删除行的完整 `cards` 表生成逐行 hash、差异计划和 manifest。
4. 按 card ID 排序分块 upsert，显式写入 local ID；成功块在 local 标为 applied，失败块保持 pending。
5. 所有行完成后写 remote ledger、校准 identity sequence、计算 remote manifest，再更新 local baseline。
6. remote manifest 与 local 不一致时发布失败，不报告成功。

验证：运行发布测试，覆盖显式 ID、sequence 校准、漂移拒绝、失败恢复、软删除更新和最终 manifest 相等。

## 第五步：desktop runtime 接入

1. 增加游戏王 runtime 配置覆盖，复用 desktop 本地数据库连接，不读取网站环境。
2. 增加导入和发布进度状态，防止同类任务并发执行。
3. 暴露获取状态、执行导入、查询批次、保存/测试/校验测试 publish target、执行/恢复发布的 oRPC 路由。
4. 所有函数和类型声明添加简短英文用途注释，错误消息不得包含连接字符串。

验证：运行 service runtime 的相关路由测试和 typecheck。

## 第六步：desktop UI

1. 更新本地设置 schema、设置 composable 和 runtime 初始化，把游戏王测试目标只保存在 desktop 本地设置中。
2. 将游戏王占位页改为固定来源、导入按钮、最近批次统计、错误摘要、测试目标配置和发布按钮。
3. UI 只描述产品行为，不展示部署实现细节、数据库密码或内部设计计划。
4. 前端默认值使用 `??`；不增加跨 package 相对导入。

验证：运行 desktop app typecheck，并检查页面没有触发自动导入或启动时写数据库。
