# 游戏王第一版卡牌数据导入设计

## 状态

已批准。local → remote 采用方案 A：保留本地自增长 ID。

## 目标

在 desktop 本地运行时中实现百鸽 `cards.zip` 的下载、校验、解析和幂等导入，将可查询的卡牌事实写入本地 PostgreSQL 的 `yugioh` schema，将来源映射、导入批次、导入状态和发布状态写入 `yugioh_data` schema，并由 desktop 将本地领域数据单向发布到测试 remote。

第一版只覆盖卡牌基础事实，不处理卡图、卡包、禁限、异画和多来源合并。

## 已验证的现状

### 现有架构与发布机制

- `docs/project-architecture.md` 将 desktop 定义为重型领域数据工作的执行权威，本地 PostgreSQL 是构建权威，remote 是发布目标。
- 现有 Hearthstone 发布链路由 desktop 直连经过配置和指纹校验的 remote。
- 现有链路在 local 记录发布批次、逐行 hash 和基线，在 remote 记录发布 ledger；发布按确定顺序分块并在事务中执行，失败后可根据未完成行恢复。
- Hearthstone 当前使用来源稳定字符串作为领域主键并会物理删除远端缺失行。游戏王要求内部自增长 `BIGINT` 和软删除，因此只复用其权威边界、目标绑定、批次、hash、事务和恢复模式，不直接复用其主键或删除实现。
- `@tcg-cards/shared` 已包含 `yugioh` 游戏名；Drizzle local/remote 配置尚未引用游戏王 schema 文件。
- `apps/site-yugioh` 存在用户未提交改动，本功能不读取或修改该目录。

### 数据源实测

2026-08-05 对 `https://ygocdb.com/api/v0/cards.zip` 做了只读检查：

- 压缩包内只有 `cards.json`。
- JSON 根节点是以来源记录键索引的对象，不是数组。
- 当前共有 14,251 条记录。
- 每条记录均有 `cid`，且根对象键与 `cid` 一致；当前 `cid` 无重复。
- 来源字段 `id` 表示候选卡密。当前有 42 条为 `0`，另有 3 条超过八位；两类值都规范化为 `NULL`。其余八位范围内的值无重复。
- 卡密在 JSON 中是 number，导入时必须转成 8 位十进制字符串并左补零。例如 `8124921` 应保存为 `08124921`。
- 验收样例 `cid=4007` 的记录为“青眼白龙”，卡密为 `89631139`。
- 当前顶层可见字段为 `cid`、`id`、`cn_name`、`sc_name`、`md_name`、`nwbbs_n`、`cnocg_n`、`jp_ruby`、`jp_name`、`en_name`、`md_en_n`、`wiki_en`、`set_ext`、`text`、`data`；部分名称字段并非每条记录都有。

数据源是可变化的外部输入。上述数量和 hash 只用于本次设计核对，不作为代码中的固定断言。

## 数据归属与依赖方向

新增表按两个维度分类：

| 表 | schema 来源轨道 | 游戏 namespace | 说明 |
| --- | --- | --- | --- |
| `cards` | shared，同时进入 local 和 remote | `yugioh` | 可独立导出的卡牌领域事实 |
| `card_sources` | local | `yugioh_data` | 来源记录到领域卡牌的映射 |
| `import_batches` | local | `yugioh_data` | 每次下载和导入的批次状态与统计 |
| `import_failures` | local | `yugioh_data` | 单条记录的结构化失败信息 |
| `import_states` | local | `yugioh_data` | 每个来源最后成功状态 |
| `publish_batches` | local | `yugioh_data` | 本地发布计划与执行状态 |
| `publish_batch_rows` | local | `yugioh_data` | 发布批次的逐卡差异和恢复状态 |
| `publish_baselines` | local | `yugioh_data` | 每个测试目标最后成功发布的本地基线 |
| `publish_ledgers` | remote | `yugioh_data` | remote 最后成功接收的发布批次 |

依赖方向严格为 `yugioh_data -> yugioh`：`card_sources.card_id` 可以引用 `yugioh.cards.id`，`yugioh.cards` 不包含任何指向 `yugioh_data` 的外键或来源状态。

本要求没有改变稳定的项目级架构边界，因此不修改中英文架构文档。

### `yugioh_data.card_sources`

| 字段 | 类型/约束 | 说明 |
| --- | --- | --- |
| `source` | `TEXT`，与 `source_record_id` 组成主键 | 第一版固定为 `ygocdb` |
| `source_record_id` | `TEXT` | `cards.json` 根对象键，是导入幂等的首要来源标识 |
| `card_id` | `BIGINT`，外键到 `yugioh.cards.id` | 对应内部卡牌；同一来源下唯一 |
| `source_hash` | `CHAR(64)` | 规范化记录的 SHA-256，用于跳过未变记录 |
| `first_seen_batch_id` | `UUID` | 首次看到该来源记录的批次 |
| `last_seen_batch_id` | `UUID` | 最近看到该来源记录的批次 |
| `retired_at` | `TIMESTAMP WITH TIME ZONE`，可空 | 来源记录消失时软停用 |
| `created_at` / `updated_at` | 带时区时间戳 | 审计时间 |

来源映射是幂等锚点。即使 `cid` 和卡密都为空，已映射记录仍能稳定更新同一个内部 ID；新记录在二者都为空时也可以先创建自增长 ID，再建立来源映射。

### 导入批次、失败和状态

`import_batches` 使用 UUID 主键，包含 `source`、固定来源 URL、压缩包 SHA-256、HTTP `etag`/`last_modified`、状态、来源记录数、`added_count`、`updated_count`、`skipped_count`、`failed_count`、`soft_deleted_count`、总错误、开始和完成时间。状态为 `running`、`completed`、`completed_with_errors`、`failed` 或 `interrupted`。

`import_failures` 使用批次 ID 与来源记录键定位错误，记录阶段、错误代码、可读消息和可选的公开来源字段快照。它不保存下载缓存、凭证或连接字符串。

`import_states` 以 `source` 为主键，记录固定 URL、最后成功批次、最后成功压缩包 hash、`etag`、`last_modified` 和更新时间。网站启动和普通前端部署不引用这些写入能力。

### 发布状态表

发布表沿用现有 Hearthstone 的职责划分，但第一版只处理 `cards` 一张领域表：

- local `publish_batches` 记录目标 ID、环境、目标指纹、manifest hash、各动作统计、状态和错误。
- local `publish_batch_rows` 记录 `card_id`、行 hash、前一 hash、`insert`/`update`/`unchanged` 动作和执行状态。软删除是一种普通 `update`，不产生物理 `delete` 动作。
- local `publish_baselines` 保存每个目标最后完成批次的 hash 基线。
- remote `publish_ledgers` 保存最后成功批次、目标指纹、manifest hash、行数和发布时间，不把 remote 变成构建权威。

## 字段规范化与校验

1. ZIP 必须由运行时在内存中读取，并且必须恰好找到一个普通文件 `cards.json`；拒绝目录穿越、额外嵌套归档和 HTML 响应。实施验证时确认 Bun 归档 API 当前面向 tar，不提供读取该 ZIP 的接口，因此采用受限 ZIP 中央目录解析器：只接受单卷、未加密、stored/deflate 方法，并校验 CRC、压缩前后大小和 UTF-8 文件名，不写入下载缓存。
2. JSON 必须是普通对象。每个根对象键作为 `source_record_id`，不使用卡名作为身份。
3. `cid` 接受正整数或 `NULL`。如果同时存在根键可解析的 cid 与记录 `cid`，两者不一致则该记录失败。
4. 来源 `id` 为 `0`、`NULL`、缺失或超过 99,999,999 时映射为 `password=NULL`；1 到 99,999,999 的整数格式化为 8 位字符串；负数属于记录错误。
5. 字符串保留 Unicode 内容并去除首尾空白；缺失和空字符串规范化为 `NULL`，正文内部换行保留。
6. 数值位掩码按整数事实保留，不在第一版中解释成枚举数组。
7. 在写库前检测当前快照内部的重复非空 `cid` 和卡密。快照级重复属于结构性危险，整批失败且不修改领域表。
8. 规范化对象采用固定字段顺序生成 SHA-256；未知字段不进入领域 hash，但会被记录到批次摘要，便于发现来源格式变化。

## 幂等导入算法

1. desktop 创建 `running` 批次，经固定 HTTPS URL 下载到内存，记录响应元数据和压缩包 SHA-256，不在仓库中创建缓存。
2. 解压并完整解析 `cards.json`，完成快照级结构检查和重复检查。下载、ZIP、JSON 根结构或快照重复失败时，将批次标为 `failed`，领域数据保持不变。
3. 按 `source_record_id` 排序处理记录，使结果和统计可重现。
4. 每条记录先规范化和校验。失败记录写入 `import_failures` 并增加 `failed_count`；其来源键仍计入“本次已看到”，避免把已有卡牌误判为来源消失。
5. 对有效记录先查 `(source, source_record_id)` 映射：
   - 已有映射：只更新映射对应的卡牌；如果新 cid 或卡密与其他卡牌冲突，该条失败，不自动合并。
   - 没有映射：分别按非空 cid 和非空卡密查找候选。两个标识命中同一张卡时建立映射；只命中一个时复用该卡；命中不同卡时该条失败；都未命中时创建新的自增长 ID 卡牌。
   - 任何情况下都不按卡名查找或合并。
6. `source_hash` 未变化且卡牌未软删除时统计为 `skipped`，只更新映射的最后看到批次；hash 变化或恢复软删除时统计为 `updated`；新建卡牌统计为 `added`。
7. 每条记录在数据库 savepoint 中执行。单条约束或写入错误只回滚该条并记入失败统计，不会静默留下半条映射；批次级连接或事务错误终止批次并保留明确错误。
8. 完整遍历后，仅对本次快照中完全缺失的 active 来源映射设置 `retired_at`。当卡牌没有任何 active 来源映射时，同时设置 `cards.deleted_at`；不物理删除卡牌。
9. 更新 `import_states` 并把批次标为 `completed` 或 `completed_with_errors`。崩溃遗留的 `running` 批次在下次启动导入时标为 `interrupted`；新批次依靠来源映射与 hash 安全续做。

连续导入相同压缩包时，第二次所有有效记录应进入 `skipped`，领域卡牌总数不增加。

## 软删除规则

- 来源快照中消失不等于物理删除，只设置来源映射 `retired_at`。
- 仅当一张卡不再有任何 active 来源映射时设置 `cards.deleted_at`。
- 来源记录重新出现时恢复原映射和原内部 ID，并清空相应的 `retired_at`、`deleted_at`。
- 发布时携带 `deleted_at`，remote 以更新表示删除；第一版发布器不执行 `DELETE FROM yugioh.cards`。
- 查询产品可见卡牌时默认增加 `deleted_at IS NULL`，审计和一致性检查可以查询全部记录。

## local → remote 自增长 ID 同步策略

### 已选方案：保留本地 ID

local 是构建权威。发布器把 `yugioh.cards.id` 连同所有领域字段显式写入 remote，并以 `id` 做 upsert。remote 的 identity 定义使用 `GENERATED BY DEFAULT`，允许发布事务显式写 ID；完成后在同一发布收尾阶段把 remote identity sequence 校准到 `MAX(id)`。

发布前预检 remote：如果相同 `id`、非空 `cid` 或非空卡密指向不同领域记录，发布失败并报告漂移，不自动覆盖或合并。remote 不提供独立批量导入入口，也不得自行创建同一批领域卡牌。

优点：

- 与现有 Hearthstone 发布时保留领域主键的模式最一致。
- local 与 remote 的领域行可以按同一 `id` 直接比较，验收和后续外键同步简单。
- 来源映射只需保留在 local；remote 服务查询不依赖 `yugioh_data`。

代价：

- 发布器必须显式管理 identity sequence，并阻止 remote 独立插入造成的主键漂移。
- remote 若已经存在不受控游戏王数据，首次发布需要先人工处理冲突；代码不会静默重编号。

### 方案 B：远端独立生成 ID，并按来源标识映射

remote 插入卡牌时自行生成 `BIGINT` ID。发布器同时把来源映射发布到 remote `yugioh_data`，以后通过 `(source, source_record_id)` 找到 remote card ID，再更新领域行。cid 和卡密只能作为冲突检查及辅助回填标识，不能代替来源映射。

优点：

- local 与 remote 的 identity sequence 完全独立，不需要显式校准。
- remote 可以维持自身内部 ID 空间。

代价：

- 与现有保留领域主键的发布模式不一致。
- local 与 remote 的内部 ID 不同；以后发布任何引用 card ID 的关系表时都必须翻译外键。
- remote 查询身份依赖 `yugioh_data` 中额外发布的来源映射，扩大了同步面和故障面。
- “领域数据一致”只能忽略内部 ID 后比较，验收和故障排查更复杂。

### 决策

采用方案 A。它最符合 desktop 作为唯一构建权威、remote 作为受限副本的现有架构，也最接近当前 Hearthstone 发布时保留主键的做法。方案 B 仅保留为被否决方案的设计记录，不进入 migration 或运行时实现。

## 发布算法

发布流程固定为：

1. 游戏王拥有独立的测试 publish target 配置，包含目标 ID、固定环境 `test`、连接字符串和通过实时数据库身份生成的指纹。连接字符串只保存在 desktop 本地设置中，不写日志、数据库或仓库。
2. 运行时拒绝环境不是 `test` 的游戏王发布，避免误连正式数据库。
3. 从 local 的全部 `yugioh.cards`（包括软删除行）生成确定性逐行 hash 和 manifest hash，与 local baseline 比较，形成新增、更新和跳过计划。第一版不形成物理删除计划。
4. 在写入前检查目标指纹、目标 ledger 和唯一标识漂移。remote 不运行导入算法，不会独立创建同一批卡牌。
5. 按 `card_id` 排序分块执行 remote 事务。每块成功后更新 local 行状态；失败块保持 pending，批次保持可恢复状态并记录具体 card ID 和错误。
6. 全部行成功后，在 remote 事务中更新 ledger，再更新 local baseline 和批次完成状态。
7. 分别从 local 和测试 remote 计算包含所有领域字段的 manifest，要求 hash 和总行数一致后才报告发布成功。

## Desktop 交互边界

- 将现有游戏王设置占位页改为最小可用工作台：显示固定来源 URL、下载并导入按钮、运行状态、最近批次四项核心统计和失败摘要。
- 同页提供独立的测试 remote 目标保存、连接测试、指纹校验和发布按钮。
- 所有数据库写入都经 `service-desktop-runtime` 执行；Nuxt 网站启动、普通前端部署和 `site-yugioh` 不获得导入或发布写入能力。
- UI 中不展示数据库密码，也不把内部实施计划写进用户可见文案。

## 错误恢复与安全

- 网络、HTTP 状态、响应类型、ZIP、JSON 和数据库错误均转成结构化批次错误，不以空成功结果掩盖。
- 快照级危险错误发生在领域写入前；单条数据错误由 savepoint 隔离并进入失败表。
- 来源键即使校验失败也计为已看到，避免错误记录触发软删除。
- 发布批次在 local 先落计划，remote 分块事务提交；进程中断后只重试 pending 行。
- remote ledger 只在所有领域行应用完成后更新。
- 第一版拒绝非 `test` 发布目标；不连接或修改正式数据库。
- 不创建或提交 `.env`、数据库文件、下载缓存、连接字符串、密码或包含密码的日志。

## 测试方案

### 单元测试

- ZIP 只接受 `cards.json`，拒绝 HTML、损坏 ZIP、路径穿越和错误根结构。
- 字段映射覆盖完整记录、缺失可选字段、`id=0 -> NULL`、七位卡密补零、负攻击/防御哨兵值和 Unicode 文本。
- 身份决策覆盖已有来源映射、只命中 cid、只命中卡密、二者命中同卡、二者冲突、二者都为空和禁止按卡名匹配。
- 同快照重复 cid/卡密导致整批失败。
- 规范化 hash 在字段顺序变化时稳定，字段值变化时改变。

### 数据库集成测试

- 第一次导入产生新增统计，第二次相同导入总数不增加且有效记录全部跳过。
- 非空 cid 和卡密唯一；没有卡密的记录仍有自增长 ID。
- 单条无效记录产生失败统计和失败明细，其他有效记录可完成；失败记录不会导致已有卡牌误软删除。
- 来源缺失只设置软删除，重新出现恢复原 ID。
- `cid=4007` 和 `password='89631139'` 查询到同一张“青眼白龙”。
- 发布失败可从 pending 行恢复；发布完成后 local/remote manifest 一致。

测试只使用隔离的临时或明确标记的测试数据库。不会运行 lint；只运行相关测试与 TypeScript typecheck。

## 验收命令与 SQL 设计

实施完成后提供可复制执行的精确命令。数据库验证至少包含：

```sql
-- 青眼白龙的两个外部标识必须指向同一内部卡牌。
select id, cid, password, sc_name, deleted_at
from yugioh.cards
where cid = 4007 or password = '89631139';

-- 非空 cid 不得重复。
select cid, count(*)
from yugioh.cards
where cid is not null
group by cid
having count(*) > 1;

-- 非空卡密不得重复。
select password, count(*)
from yugioh.cards
where password is not null
group by password
having count(*) > 1;

-- 无卡密记录仍必须拥有内部 ID。
select count(*) as cards_without_password,
       count(id) as cards_without_password_with_id
from yugioh.cards
where password is null;

-- 查看最近两次导入统计，确认第二次没有新增。
select id, status, added_count, updated_count, skipped_count,
       failed_count, soft_deleted_count, completed_at
from yugioh_data.import_batches
order by started_at desc
limit 2;
```

local/remote 一致性命令把 `id` 纳入 manifest，并要求两端内部 ID 完全一致。

## 预计实施范围

实施预计只触及以下直接相关区域：

- `packages/db`：游戏王 shared/local/remote schema、导出、Drizzle 配置和由 `drizzle-kit generate` 生成的 local/remote migrations。
- `apps/service-desktop-runtime`：游戏王 ZIP 解析、导入、测试 remote 目标校验、发布、进度和 oRPC 路由及相关测试。
- `apps/app-console-desktop`：游戏王设置页、最小 composable 和 desktop 本地设置类型/校验。
- `specs/yugioh-card-import`：确认后的 `design.md`、todo 优先的 `plan.md`；实现完成后按仓库规则归档并添加 `summary.md`。

不修改 `site-main`、`site-magic`、`site-console`、`watcher`、`site-yugioh` 或其他游戏功能，也不做顺手重构。

## 已确认决策

local → remote 保留本地自增长 ID；remote 不独立生成同一批领域卡牌 ID。
