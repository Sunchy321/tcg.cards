# 0024: Accelerated search routes by capability and keeps the original PostgreSQL path

Every game's search request is planned statically — with no database call — into one of three coverage plans against the target backend's declared capabilities: `exact`, where the accelerated backend alone decides results, order, total, and ambit landing; `candidate`, where the backend narrows a safe superset and the original PostgreSQL path verifies the untouched query in one statement before paging, counting, or widening ambit; or `original`, where the unchanged domain-table query runs the whole request. The plan follows capability, never boolean complexity, so a deep AND/OR/NOT expression over supported fields is still `exact`, while one unsupported feature — an uncovered field, an unknown enum value, an unproven regex, a print-scoped command, a missing manifest, or a data-version mismatch — sends the whole request to `original`. Candidates may never drop a result under OR or NOT, and a page is never cut before verification.

The original PostgreSQL path is retained permanently and is never altered because a planner exists (expand–contract, not replace). The cost is two maintained search paths per game; the benefit is that coverage can grow one capability at a time, every unsupported or unverified request still returns the same answer it did before, and a store whose data is unready, unpublished, or out of version can be switched off without a user-visible regression. The alternative — cutting the original path over once acceleration covered the common cases — was rejected because several paths fall back by design (ordinary Magic `r:`, Hearthstone hashtag and faction queries, local packages lacking a capability) and because independent store activation (ADR-0023) depends on a path that is always available.

A backend ships only after a same-data, same-semantics measurement shows reproducible, attributable gains per workload group with an identity-level correctness check against the original path; an unmeasured store is reported as unverified rather than extrapolated from another. Under that rule the first integration scope covers both games' PostgreSQL acceleration and the Hearthstone local package; the Magic local package waits until its text and rarity-summary results converge with PostgreSQL, and D1 waits for a real-environment measurement.
