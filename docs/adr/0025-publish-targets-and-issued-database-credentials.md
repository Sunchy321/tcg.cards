# 0025: Publishing binds to named targets and reaches the remote through issued credentials

Publishing is bound to publish targets the maintainer creates and names, selected per publish rather than configured per game. A direct target carries its own database connection and publishes without console admission. An account target is the remote itself: the desktop logs in, service-console-api checks the account's per-game data permission, issues a short-lived credential for a per-account publish role with `VALID UNTIL` and a rotated password, and the desktop still writes to PostgreSQL directly. PostgreSQL data never travels through the service, so ADR-0021's reason for keeping the direct-database path — bulk writes do not fit an API hop — still holds; the account model adds credential issuance and admission, not a second data path.

The stores that cannot be reached directly follow the platform instead. D1 is only writable by the Worker that holds its binding, so service-console-api executes the publish statements. Search SQLite packages are uploaded straight to R2 through URLs the service presigns, keeping the bulk bytes off the Worker; the desktop writes the manifest locally after the service has verified that every referenced object exists at its expected size. Content integrity is not re-verified by the service: objects are addressed by their SHA-256 and the downloading client recomputes hashes and the release hash before activating anything. A direct target may still generate search packages and a manifest locally, but it never uploads them.

Rejected alternatives: proxying every write through service-console-api (Worker request and duration limits, plus a second bulk path to maintain); handing the desktop long-lived database and R2 credentials (a stored key with no boundary, which is what the account target exists to remove); and re-hashing uploaded objects inside the Worker (hundreds of megabytes per release for a check the client already performs). The consequence is that service-console-api must hold one privileged database role for role issuance and password rotation, the publish stream key becomes `(game, target, publishType)`, and the former per-game publish rows and R2 secrets are removed without migration.
