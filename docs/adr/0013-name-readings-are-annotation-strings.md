# Name readings are annotation strings stored beside the name, never merged into it

When an official card name carries a phonetic gloss — Japanese furigana being the motivating case, and any game's localized names qualify — the reading is stored in its own column as an **annotation string**: each annotated run of the name is followed immediately by its reading in parentheses, `包囲（ほうい）の搭（とう）`. Unannotated text is literal, and a reading contains only kana, never a parenthesis, so the format parses without ambiguity; a name that itself carries a literal parenthesis would make the string unparseable, and such strings are rejected by validation rather than guessed at. Full-width parentheses are the storage form — the native shape of the Japanese sources — and half-width parentheses are accepted on input and normalized. The name column always holds the plain printed name. Display renders the annotation as ruby over exactly the annotated runs; an absent annotation renders the plain name, and an annotation whose base text does not match the displayed name character for character is dropped. The full reading is recovered by parsing the annotation string, and that parsed reading is what kana search and kana ordering consume.

The annotation is a fact of the printed surface, so it lives where the printed name lives, and it reaches every derived display row by riding the same derivation the name itself already follows — the same joins, the same per-face segmentation, the same projection. It carries the same trust semantics as the text it annotates: algorithmically drafted annotations are not shown until they are reviewed, because a wrong reading is worse than no reading, and absence is a normal state that degrades to the plain name.

**Why:** No machine-readable source supplies furigana, so the design must treat missing data as the norm and make the annotation purely additive: nothing about storage, search or display changes until data arrives, reviewed data lights up ruby, and bad or stale data degrades safely. Keeping the annotation out of the name column is what makes it additive — every existing consumer of a name (search matching, plain-text contexts, the joined-face segmentation of localized text) keeps reading one literal string, and the display layer is the only place that learns the notation.

**Considered options:** merging the reading into the name column with an inline notation (rejected: every consumer must then strip or parse it, and plain-text contexts leak the notation), two parallel columns holding a clean name and a flat full reading (rejected as the display source — a flat reading cannot be aligned onto name segments reliably under irregular readings, and a misaligned ruby is worse than none; the flat reading survives only as the parsed derivative of the annotation string for search and ordering), aligning the reading onto the name at render time (rejected for the same wrong-ruby reason, and it would put the fragile code on every request), and structured segments in JSONB (rejected: annotations must ride the same text joins and per-face segmentation the names ride, and reviewers author and correct prose-shaped text far more easily than structures).

**Placement:** the reading's text of record is not a column of the localization authority. The authority is the record of localized text from the scryfall/MTGCH chain, while readings arrive from other sources, so they keep a mapping table of their own in the data schema — one row per language and name, mapping the name currently in use to its annotation string, with per-print exceptions (`set:number`) for names whose printed reading differs between printings and a draft/reviewed status (only reviewed rows take effect). The mapping reaches the printed surfaces and the derived display rows through projection: one resolution function reads the mapping and fills a `ruby_*` column beside every name column, and a ruby write updates the mapping and the affected result rows together, so the stored annotation can never drift from the displayed one.
