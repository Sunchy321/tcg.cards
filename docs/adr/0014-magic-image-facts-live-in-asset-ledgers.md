# Magic image facts live in per-game asset ledgers, not in the fact tables

A print's image fact — that a file exists at a canonical key, with a given content hash, dimensions, byte size, provenance, and quality — used to live only on the fact-table row (`prints.image_status` / `prints.image_info`), preserved across re-projections by a step that copied those columns from the fact table's own previous state. That made the fact table the sole home of facts the projection cannot derive from raw data: wiping the fact tables destroyed every image fact irrecoverably, and an empty image slot then let a download sweep overwrite a hand-made scan with a fetched stand-in. Image facts now live in a **per-game asset ledger** — `asset_images` in each game's `{game}_data` schema, one row per file in the asset store, keyed by the store key — and the projection fills the prints' image fields from that ledger. The fact-table columns remain as the serving contract but are derived truth.

**Why:** the image fact is import-side state about a file, not a fact the raw sources can re-derive: scryfall's raw rows supply a download URL and a source-side status, but nothing about the local bytes, their provenance, or their measured quality. Placing that state outside the fact tables makes the fact tables disposable — a wipe and re-projection restores image fields exactly — and gives the never-overwrite rule a home that survives the same wipe: the upload-group protection and the placeholder tombstones are read from the ledger by key, so a cleared fact row can no longer lift the protection off a curated image.

**Considered options:** a print-grain ledger mirroring `image_info` one row per print face (rejected: it inherits the fact table's identity — a vanished print strands its row, and the asset directory cannot be audited against it), a content-addressed ledger like hearthstone's render-hash assets (rejected for magic: scans are not regenerable from a formula, so each file belongs to exactly one print, the folder layout already encodes the print identity in the key, and nothing dedupes today — the shared `sha256` column keeps the content identity available should that ever change), and a grab-bag jsonb payload column for game-specific fields (rejected: the ledger's value is queryability — audit, duplicate lookup, orphan enumeration — and jsonb recreates the opacity of the `image_info` blob this design removes; game-specific needs arrive as typed extension columns beside the shared factory's columns).

**Grain and scope:** one row per file, not per content — the same artwork printed under two collector numbers stores two files and two rows, mirroring the asset store exactly, because the alternative (content addressing) buys dedup that magic's import flow does not use while costing the direct key-to-row correspondence every writer and reader relies on. The ledger records images only; other asset kinds (video, audio) are expected to follow the same pattern as their own `asset_<type>` tables rather than grow this one, and the generic `asset_files` fallback stays unbuilt until a need names itself.

**Tombstones:** the one deliberate exception to "a row asserts a file exists" is a row whose status is `placeholder` — it asserts that a key deliberately has no image and that download tasks must never fetch one. Clear and mark write tombstones when their result is the placeholder state, the remote import treats them as a hard skip, and the projection renders them as the placeholder badge with empty metadata. The reset memory therefore lives in the ledger too, where a fact-table rebuild cannot wash it away; before this design it survived only as a fact-table column re-derived from scryfall's raw status, which could not express a deliberate local reset at all.

**Placement:** the ledger is per-game `{game}_data`, sharing one column factory so the games stay structurally compatible without pretending every game fills every column — the factory admits only columns every game's pipeline is guaranteed to supply, and magic's quality status and score sit beside them as magic's own extension columns. The projection is the single writer of the fact-table image columns; imports write the ledger and the files, and never the fact rows' image fields directly.
